# 任务类型配方：先分类，再抓药

> 源：PDF 第 5 章（配方组合、先发散再收敛、先推理后结论、隐式语义）
> 因目标含糊、信息不足或多类歧义而判别不清时不要硬猜——这是关键缺口，反问用户（见 five-elements.md）；目标清楚但五类均不匹配时，走 SKILL.md 的零类出口。

## 类型判别速查

| 类型 | 判别特征 |
| --- | --- |
| 学习理解类 | 解释概念/代码/报错，"X 是什么""这段在干嘛" |
| 工程执行类 | debug、改码、修构建、跑通某功能；代码评审/review diff（只读审查） |
| 决策比较类 | 选项已存在：A/B/C 选哪个、要不要重构 |
| 猜想探索类 | 选项不存在的开放问题："怎么设计""有什么创新点""还有什么可能" |
| 内容生成类 | 写文档、注释、README、报告、脚本 |

## 学习理解类

- 判别特征：解释概念/代码/报错，"X 是什么""这段在干嘛"。
- 催化剂配方：先讲直觉 + 最小例子 + 检查理解（解释类为主）。
- 默认限制（缺失时标【推断】）：先建立必要直觉；专业术语首次出现时给出简短定义。
- 默认验收（缺失时标【推断】）：我能复述核心思想 + 出一道判断题检查理解。
- 转写模板：

```text
目标：清楚解释 <对象>，先整体作用再分模块
[背景：<用户已明确的知识水平或使用场景；不影响回答时整行省略>]
材料：<粘贴代码/概念名/报错>
限制：【推断】每个术语第一次出现时解释；每次只引入一个新概念 ← 可改
处理方法：先讲直觉再讲定义；用一个最小例子
验收：【推断】最后出一道题检查我是否真正理解 ← 标准可改
```

## 工程执行类

- 判别特征：debug、改码、修构建、跑通某功能；代码评审/review diff 也归入本类，但走只读评审配方。
- 修改/调试催化剂配方：先拆解原因 + 最小修改 + 测试验证（拆解类 + 执行类 + 验证类各取一）。
- 代码评审催化剂配方：核对 diff 意图与实际控制流/数据流 + 用代码证据验证每个问题 + 保守评定严重性。
- 修改/调试默认限制（缺失时标【推断】）：先不要改代码，只分析原因；不要给危险命令（删文件/重装环境）；不要修改无关文件。
- 修改/调试默认验收（缺失时标【推断】）：构建通过/原有测试全过 + 说明修改内容与回滚方法。
- 代码评审默认限制（缺失时标【推断】）：只审查，不修改代码；严重性评级保守；只报告能从代码确认的问题；每个问题按 `文件:行` 引用。
- 代码评审默认验收（缺失时标【推断】）：按严重性排序的问题清单；每项包含 `文件:行`、代码证据、影响与最小修复方向；无法确认的内容不作为问题报告。
- 领域结构：回答容易太泛、遗漏维度或关系不清时（性能排查、状态类 bug、坐标系
  问题等），在处理方法或验收中加入合适的观察结构（耗时预算表、状态转移表、
  坐标表等，见 domain-structures.md）；表中无法确认的项标"待验证"。
- 修改/调试转写模板：

```text
目标：定位并修复 <问题>，优先最小修改
[背景：<已明确且会影响排查或方案的项目环境；不影响回答时整行省略>]
材料：<粘贴报错/日志/相关代码>
限制：【推断】先列原因再动手；不要删除依赖；不要改无关文件 ← 可改
处理方法：先列可能原因按概率排序，选最小修改方案；改后运行测试
验收：【推断】<构建命令> 通过；说明改了什么、怎么回滚；需要我补什么信息就直接问 ← 标准可改
```

- 代码评审转写模板：

```text
目标：审查 <diff/commit/文件范围>，只报告会影响正确性、安全性、性能或可维护性的可确认问题，不修改代码
材料：<粘贴 diff，并提供必要的相关文件或提交范围>
限制：【推断】严重性评级保守；只报告能从代码确认的问题；每个问题按 `文件:行` 引用 ← 可改
处理方法：先确认改动意图，再沿实际控制流和数据流核对行为；逐项用代码证据验证，无法确认的内容不作为问题报告
验收：【推断】按严重性排序的问题清单；每项包含 `文件:行`、代码证据、影响与最小修复方向 ← 标准可改
```

## 决策比较类

- 判别特征：选项已存在：A/B/C 选哪个、要不要重构。
- 只比较时不触发：只要求比较、不要求推荐、筛选或判断某个既有结论是否改变时，统一比较维度，不加入独立反方审查，也不凭空推荐；对全部候选项逐项、对称地列出反方观点仍属于只比较。
- 要求推荐或筛选：先统一比较维度，再执行对应模式的独立反方审查（严谨类为主）。
- 指定方案反驳不要求统一比较维度：当用户把明确指定的方案或既有结论作为非对称攻击对象时，直接攻击该对象；即使用户不要求判断原结论是否改变，也触发独立反方审查；不得比较或展开替代方案，并尊重用户禁止改判结论的边界。
- 要点：先完成统一分析，再执行用户要求的终点动作；不要把“比较”自动改写成“推荐”。
- 默认限制（缺失时标【推断】）：使用同一口径比较全部选项；不要顺着我已有的倾向圆。
- 默认验收（缺失时标【推断】）：每个选项在同一组维度下有分析；只交付用户要求的比较、推荐、筛选或反驳结果。
- 只比较模板：

```text
目标：比较 <A/B/C>，不做推荐
[背景：<已明确且会改变比较结果的使用场景、既有环境或团队结构；无实质影响时整行省略>]
材料：<各选项的现状/材料>
限制：【推断】使用同一口径比较全部选项；不排序、不推荐、不替用户作决定 ← 可改
处理方法：从成本、难度、风险、长期维护四个维度统一比较，说明各自适用边界
验收：【推断】比较表 + 每个选项的优势、代价与适用条件；不输出推荐结论 ← 标准可改
```

- 需要推荐时的模板：

```text
目标：比较 <A/B/C>，先不下结论
[背景：<已明确且会改变比较结果的使用场景、既有环境或团队结构；无实质影响时整行省略>]
材料：<各选项的现状/材料>
限制：【推断】先完成全部比较再给推荐；不要顺着我已有的倾向圆 ← 可改
处理方法：从成本、难度、风险、长期维护四个维度统一比较并形成初步推荐；执行独立反方审查：支持多 agent 时派发一个未参与初步分析的子 agent 尝试推翻推荐，不支持子 agent 时单独做一遍同标准红队审查；最后综合反驳，说明最终推荐是否改变
验收：【推断】比较表 + 推荐 + 最强反方观点 + 反驳成立与否 + 最终推荐是否改变 + 什么情况下应改选其他项 ← 标准可改
```

- 推荐审查：按上面模板说明最终推荐是否改变。
- 筛选审查：把“初步推荐”替换为“初步候选集”，要求审查者挑战纳入/排除理由和阈值，并说明候选集是否改变。
- 指定方案反驳：不生成推荐，不比较替代方案，直接审查用户指定方案；默认说明原判断是否改变，用户禁止时只说明反驳成立范围。

## 猜想探索类（两段式输出）

- 判别特征：选项不存在的开放问题："怎么设计""有什么创新点""还有什么可能"。
- 催化剂配方：先发散（禁止过早给最终方案）→ 再收敛（按明确标准筛选）。
- 默认限制（缺失时标【推断】）：发散阶段不要收敛、不要评分排序；每个方向给一段核心思路即可。
- 默认验收（缺失时标【推断】）：发散阶段至少 4 个方向，每个含核心思路与主要代价；收敛阶段给出最推荐的 1-2 个方案、独立反方审查结果、推荐是否改变，以及第一步行动。
- 转写模板：产出下面两条提示词，等 AI 展开完再发第二条；鼓励用户在两条之间补充自己的筛选偏好。

第一条（发散）模板：

```text
目标：探索 <问题> 的可能方向，先不要给最终方案
[背景：<已明确且会改变探索范围的描述性场景或既有环境；无实质影响时整行省略>]
材料：<现状/已有条件>
限制：【推断】现在不要收敛、不要评分排序；每个方向给一段核心思路即可 ← 可改
处理方法：从常规方案、低成本方案、激进方案、长期方案四个角度展开【推断-角度可换】
验收：【推断】至少 4 个方向，每个含核心思路与主要代价 ← 标准可改
```

第二条（收敛）模板：

探索提示词 2 必须包含目标、材料、限制、处理方法、验收；背景单独执行删除测试：

```text
目标：基于上一轮候选方向，筛选并推荐最值得优先推进的 1–2 个方向
[背景：<用户或上一轮已明确、且会改变筛选结果的场景；无实质影响时整行省略>]
材料：<粘贴提示词 1 的完整输出>；<补充筛选偏好，没有则写“无”>
限制：【推断】只基于上一轮候选和补充材料比较；不虚构项目事实 ← 可改
处理方法：按实现难度、成本、稳定性、可维护性统一比较【推断-标准可换】并形成初步推荐；执行独立反方审查：支持多 agent 时派发一个未参与初步分析的子 agent 尝试推翻推荐，不支持子 agent 时单独做一遍同标准红队审查；最后综合反驳，说明最终推荐是否改变
验收：【推断】推荐 1–2 个方向 + 推荐理由 + 适用边界 + 最强反方观点 + 反驳成立与否 + 最终推荐是否改变 + 第一步行动 ← 标准可改
```

## 术语未知时的两段式：引导采样 → 上下文回滚

- 触发条件：用户能描述现象，但明确表示不知道它在专业上叫什么，且后续要做
  工程分析。只想知道名词、不打算继续排查的，按学习理解类正常转写。
- 原理：前半段先让 AI 根据现象提出候选概念（引导采样）；后半段清理试探过程
  产生的噪声，只带已确认事实、必要材料、候选方向和验收标准，新开干净会话
  重新开始真正的工程分析（上下文回滚——回滚的是对话上下文，不是 Git）。
- 输出两条提示词，中间提醒用户：拿候选术语对照代码、配置和日志核实后，
  **新开一个干净会话**再发第二条；旧对话里的试探、误解和已排除方向不要带过去。

第一条（引导采样）模板：

```text
目标：帮我给下述现象"起名字"，先不要给修复方案，也不要修改代码
材料：<用自己的话描述现象>
限制：【推断】暂时不下结论，不猜测具体根因 ← 可改
处理方法：1. 把我的描述整理成已观察到的事实；2. 给出 5–8 个可能相关的技术概念，各用一句话解释；3. 区分哪些概念有现有证据支持、哪些只是待验证的候选方向
验收：【推断】事实清单 + 候选概念清单，每个概念含一句话解释与证据状态 ← 可改
```

第二条（干净会话中的工程分析）模板：

```text
目标：定位 <已命名现象> 的原因，先分析，不改代码
材料：已确认现象：<核实后的事实清单>；候选方向：<核实后保留的概念>；<粘贴相关代码/日志>
限制：候选方向不是已确认结论，必须从代码和日志中验证；将已确认事实、代码证据和推测分开写；【推断】不要直接重写相关模块 ← 可改
处理方法：先列可能原因并按概率排序，再说明每个原因对应的日志字段或最小验证方法
验收：按优先级排列的可能原因 + 每项的验证方法 + 指出下一步需要我提供哪些文件
```

- 要点："AI 说这个现象可能叫 X"和"代码已经证明根因是 X"完全不是一回事；
  候选方向必须由用户结合真实材料核实后才能进入第二条。

## 内容生成类

- 判别特征：写文档、注释、README、报告、脚本。
- 催化剂配方：格式例子（隐式语义）+ 明确验收。
- 要点：一个高质量例子比一大段格式描述更有效；例子会把 AI 带进正确状态。
- 默认限制（缺失时标【推断】）：格式仿照下面的例子；不要超过 <长度>。
- 默认验收（缺失时标【推断】）：格式与例子一致 + 覆盖 <必须包含的内容点>。
- 转写模板：

```text
目标：写 <文档/注释/脚本>
[背景：<已明确且会改变内容难度或形式的受众/使用场景；无实质影响时整行省略>]
材料：<素材/代码/要点>
限制：【推断】格式仿照下面的例子；不要超过 <长度> ← 格式可改
处理方法：先列大纲让我确认，再写全文
验收：【推断】包含 <要点清单>；风格与例子一致 ← 要点可改
例子：<贴一段目标风格的样例>
```

## 通用纪律（各类型都适用）

- 背景逐项诊断但条件输出：通过删除测试才保留，不能为填模板推断用户身份或能力，也不能复述目标或材料中已有的信息。
- 独立反方审查只用于推荐审查、筛选审查或指定方案反驳；它整体计为一个严谨类催化剂。
- 不写死步骤：给目标和边界，不给"必须先 ls 再 cat"——写死会把 AI
  困在使用者的认知上限，失去寻优能力。
- 限制优先写正向可检查标准（长度、结构、术语处理、"待验证"标记），保留 1–2 条
  关键禁止即可，不堆一长串"不要"（AP8）。
- 长 agent 任务主线锚点：用户描述、或会话内可直接观察到当前执行出现"AI 修着修着跑去处理别的问题、越干越偏"等
  语义漂移症状时，在限制中加入——"当前唯一目标：<X>。处理中发现的其他问题：
  先记录到候选问题列表；除非会阻塞当前任务，否则不要立即处理；每完成一个阶段，
  重新检查是否更接近验收标准。"
- 上下文污染重时（旧对话已积累大量错误假设、无关代码和被排除的方向），仅靠
  重置锚点往往不够：把“建议新开会话，只带确认过的事实和必要材料”纳入解说末行；
  与检查推断/占位符、核对收割内容等其他末行提醒同时触发时合并为一句。
- 环境适配：目标是会改文件跑命令的 coding agent，且任务是修改/调试 → 强调最小修改/测试/回滚；
  只读代码评审 → 使用评审专用限制与验收，不要求改码或回滚；目标是聊天 AI → 强调理解难度控制与输出结构。
