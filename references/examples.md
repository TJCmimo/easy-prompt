## 例 1（工程执行类·金标准，含完整输出格式）

人话：帮我看看这个识别代码为啥掉帧

诊断：工程执行类；关键缺口无（目标可从"掉帧"析出）；
缺背景/输入/限制/验收；命中 AP1（"帮我看看"）。

转写输出（完整格式，逐字示范）：

─── 优化后的提示词（直接复制）───────
目标：定位装甲板识别代码掉帧的原因，先分析，不改代码
背景：【推断】RM 视觉组新生，C++ 基础一般 ← 不符请改
输入：<在此粘贴识别相关代码与运行日志/帧率数据>
限制：【推断】先不要改代码；不要建议重装环境或删除文件 ← 可改
处理方法：先列可能原因并按概率排序（相机采集/图像处理耗时/锁与拷贝/日志 IO），再给每项的排查步骤
验收：【推断】按概率排序的原因清单 + 每项对应的验证命令或计时打点位置 ← 可改
─── 改动说明 ───────────────────
· 原话"帮我看看"目标模糊（AP1）→ 细化为"定位掉帧原因，先分析不改码"
· 背景、限制和验收均为【推断】，不符可改
· 发送前补齐代码、日志和帧率数据等输入占位符，并检查所有【推断】行

人话：CMakeLists 每行都是啥意思啊看不懂

诊断：学习理解类；缺背景（水平）与输入（文件内容）；无反模式。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
目标：用适合初学者的方式解释这份 CMakeLists.txt，先讲整体作用，再逐行说明
背景：【推断】RM 视觉组新生，CMake 基础一般 ← 不符请改
输入：<在此粘贴 CMakeLists.txt 全文>
限制：【推断】不要一开始堆专业术语；每次只引入一个新概念 ← 可改

─── 改动说明 ───────────────────

## 例 3（决策比较类）

人话：我觉得咱们自瞄该用 EKF，你说说为啥 EKF 好

诊断：决策比较类；命中 AP2（先给结论求辩护）；缺比较对象与场景输入。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
目标：比较 EKF、匀速卡尔曼和自适应滤波在 RM 自瞄中的适用性，先不下结论
背景：【推断】RM 队内自瞄项目，维护者以新生为主 ← 不符请改
输入：<补充当前自瞄场景、运动模型、算力预算、现有滤波方案与观测噪声数据>
限制：【推断】先完成全部比较再给推荐；不要顺着我已有的 EKF 倾向圆 ← 可改
处理方法：统一按精度、计算量、调参难度、新手可维护性四个维度比较；对推荐项给出最强的反方观点
验收：【推断】比较表 + 明确推荐 + 推荐理由 + 什么情况下应改选其他项 ← 可改
─── 改动说明 ───────────────────
· 原话先认定 EKF 再求理由（AP2）→ 改为三种方案先比较、最后推荐
· 用同一组维度比较，并要求对推荐项给出最强的反方观点，避免只替既有倾向辩护
· 你没给自瞄场景与数据 → 留了占位符；背景、限制和验收均标为【推断】，可按实际情况修改

输入：<在此粘贴目标系统版本、项目仓库信息、依赖清单、已验证命令与常见报错素材>

```bash
<安装命令>
```
