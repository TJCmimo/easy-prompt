## 例 1（工程执行类·金标准，含完整输出格式）

人话：帮我看看这个装甲板识别代码为啥掉帧

诊断：工程执行类；关键缺口无（目标可从"掉帧"析出）；
背景判定：省略——用户身份或能力不会改变掉帧排查；缺材料/限制/验收；命中 AP1（"帮我看看"）。

转写输出（完整格式，逐字示范）：

─── 优化后的提示词（直接复制）───────
```text
目标：定位装甲板识别代码掉帧的原因，先分析，不改代码
材料：<在此粘贴识别相关代码与运行日志/帧率数据>
限制：【推断】先不要改代码；不要建议重装环境或删除文件 ← 可改
处理方法：先列可能原因并按概率排序（相机采集/图像处理耗时/锁与拷贝/日志 IO），再给每项的排查步骤
验收：【推断】按概率排序的原因清单 + 每项对应的验证命令或计时打点位置 ← 可改
```
─── 改动说明 ───────────────────
· 原话"帮我看看"目标模糊（AP1）→ 细化为"定位掉帧原因，先分析不改码"
· 用户身份和能力不影响排查路线 → 背景通过删除测试后整行省略；限制和验收为【推断】
· 发送前补齐代码、日志和帧率数据等材料占位符，并检查所有【推断】行

## 例 2（学习理解类）

人话：我是 RM 视觉组新生，CMake 基础一般，想看懂 CMakeLists 每行是什么意思

诊断：学习理解类；背景判定：保留——用户明确给出的水平会改变解释难度；缺材料（文件内容）；无反模式。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
```text
目标：解释这份 CMakeLists.txt，先讲整体作用，再逐行说明
背景：读者是 RM 视觉组新生，CMake 基础一般
材料：<在此粘贴 CMakeLists.txt 全文>
限制：【推断】不要一开始堆专业术语；每次只引入一个新概念 ← 可改
处理方法：先讲直觉，再讲正式定义；每个专业术语第一次出现时都解释
验收：【推断】逐行解释覆盖粘贴内容；最后出一道判断题检查我是否真正理解 ← 可改
```
─── 改动说明 ───────────────────
· 把“看不懂”细化为“先讲整体作用，再逐行说明”，对应学习理解类
· 处理方法采用“先讲直觉，再讲正式定义”和“每个专业术语第一次出现时都解释”
· 你明确给出的学习背景会改变讲解难度，因此保留；没贴文件内容则留下占位符
· 限制和判断题验收为【推断】，可按需修改
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 3（决策比较类）

人话：我们 RM 自瞄项目每年换届，维护者以新生为主。我觉得该用 EKF，你说说为啥 EKF 好

诊断：决策比较类；背景判定：保留——换届频率和维护者水平会改变可维护性权重，且没有在目标或材料中重复；命中 AP2（先给结论求辩护）；缺比较对象与场景材料。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
```text
目标：比较 EKF、匀速卡尔曼和自适应滤波在 RM 自瞄中的适用性，先不下结论
背景：项目每年换届，维护者以新生为主
材料：<补充当前自瞄场景、运动模型、算力预算、现有滤波方案与观测噪声数据>
限制：【推断】先完成全部比较再给推荐；不要顺着我已有的 EKF 倾向圆 ← 可改
处理方法：统一按精度、计算量、调参难度、可维护性四个维度比较并形成初步推荐；执行独立反方审查：支持多 agent 时派发一个未参与初步分析的子 agent 尝试推翻推荐，不支持子 agent 时单独做一遍同标准红队审查；最后综合反驳
验收：【推断】比较表 + 明确推荐 + 推荐理由 + 最强反方观点 + 反驳成立与否 + 最终推荐是否改变 + 什么情况下应改选其他项 ← 可改
```
─── 改动说明 ───────────────────
· 原话先认定 EKF 再求理由（AP2）→ 改为三种方案先比较、最后推荐
· 用同一组维度比较，并用独立批评者专门尝试推翻初步推荐，降低主 agent 自审偏乐观的风险
· 换届和维护者背景来自原话且会改变维护成本判断；缺失的场景与数据保留为材料占位符
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 4（猜想探索类·两段式）

人话：我们的 RM 哨兵导航项目人手和经费有限，还有哪些可以创新的方向？

诊断：猜想探索类；背景判定：省略——RM 哨兵导航已在目标中，人手和经费属于资源限制；缺现状材料与收敛标准。
本例同时示范：两条提示词都逐项诊断背景，并把资源上限放入限制而不是背景。

转写输出（完整格式）：

─── 优化后的提示词 1（先发散，直接复制）───
```text

限制：项目人手和经费有限；【推断】现在不要收敛、不要评分排序；每个方向给一段核心思路即可 ← 可改
处理方法：从常规方案、低成本方案、激进方案、长期方案四个角度展开【推断-角度可换】
验收：【推断】至少 4 个方向，每个包含核心思路与主要代价 ← 标准可改
```

等 AI 展开完再发第二条，可先补充你的筛选偏好。
（补充我的筛选偏好：______）

─── 优化后的提示词 2（再收敛，直接复制）───
```text
目标：基于上一轮哨兵导航候选方向，筛选并推荐最值得优先推进的 1–2 个方向
```

· 现状信息未提供 → 第一条保留材料占位符；人手和经费来自原话并归入限制，不当作背景
· 第二条只在 AI 展开后发送，并用独立反方审查检验初步推荐；筛选标准、限制与验收中的推断均已标明

## 例 5（内容生成类）

人话：帮我给第一次配置项目环境的 RM 视觉组新队员写一份环境配置文档

诊断：内容生成类；背景判定：保留——目标读者由用户明确给出并会改变写法；缺素材、格式例子与验收。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
````text
目标：编写项目环境配置文档
背景：读者是第一次配置项目环境的 RM 视觉组新队员
材料：<在此粘贴目标系统版本、项目仓库信息、依赖清单、已验证命令与常见报错素材>
限制：格式仿照下面的目标风格样例（隐式语义）；【推断】使用简体中文 Markdown ← 格式可改
处理方法：先列大纲让我确认，再写全文
验收：【推断】必须覆盖系统版本、依赖安装、常见报错三块；风格与样例一致 ← 要点可改

### 安装 <依赖名>

```bash
````

─── 改动说明 ───────────────────

· 加入目标风格样例传递隐式语义，并用“先列大纲让我确认，再写全文”控制生成过程
· 验收补上系统版本、依赖安装、常见报错三块，因原话未指定而标为【推断】可改
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 6（会话收割·面向 coding agent）

人话：把我们刚才排查 cache shutdown 竞态的内容收成一条提示词，我要 rewind 后交给 coding agent 继续修。

会话上文已确认：唯一目标是修复 TSAN 报告的 cache shutdown 竞态；相关文件为
`src/cache.cpp`、`tests/cache_test.cpp`；失败命令和 TSAN 重跑命令已经执行并贴出结果；
240 行日志位于 `/tmp/cache-tsan.log`。AI 曾无证据断言“根因就是 ABA”，该断言不收割。

诊断：工程执行类；材料齐全，无关键缺口；长日志只收关键片段并注明来源。
面向 coding agent 且成品将在 rewind 后使用，因此采用完整字段；提示词内不留占位符。

转写输出（收割场景金标准）：

─── 优化后的提示词（直接复制）───────
```text
目标：定位并修复 Cache 关闭阶段由 `Cache::shutdown()` 与完成回调并发访问引发的数据竞争，优先最小修改

材料：
- 实现文件：`src/cache.cpp`
- 测试文件：`tests/cache_test.cpp`
- 已观察失败：`cache_test` 在关闭阶段仍收到一次完成回调
- TSAN 关键片段：
  `WARNING: ThreadSanitizer: data race`
  `Write of size 1 at Cache::shutdown() src/cache.cpp:184`
  `Previous read of size 1 at Cache::onComplete() src/cache.cpp:127`
- 完整日志来源：`/tmp/cache-tsan.log`
- 已执行失败命令：`ctest --test-dir build -R cache --output-on-failure`
- 已执行 TSAN 命令：`TSAN_OPTIONS=halt_on_error=1 ctest --test-dir build-tsan -R cache --output-on-failure`

限制：只修改消除该数据竞争所必需的代码，不改无关文件；把代码或日志能确认的事实与候选解释分开；发现其他问题先记录，除非阻塞本任务否则不处理

处理方法：沿 `Cache::shutdown()` 与 `Cache::onComplete()` 的对象生命周期、同步关系和退出顺序核对实际控制流；用上述代码与 TSAN 证据验证根因后实施最小修复；改后重跑两条命令

验收：两条命令均通过，TSAN 不再报告上述竞争；说明修改文件、根因证据、验证结果与回滚方法
```
─── 改动说明 ───────────────────
· 把已确认的文件、函数、失败现象和两条命令直接收割进材料与验收，成品不依赖旧对话。
· 240 行 TSAN 日志只保留能支持任务的关键片段，并注明完整日志来源。
· 无证据的“ABA 根因”没有写成事实；coding agent 的 rewind 场景保留完整字段且不留占位符。
· 发送前确认没有未处理的【推断】或占位符，并核对收割的路径、命令、日志片段与事实，核对后回溯发送。

人话：用大白话解释 RAII，并给一个最小例子。

诊断：学习理解类；单一明确目标，无需收割或粘贴材料，也无特殊限制，使用弹性格式。

转写输出（弹性格式，逐字示范）：

─── 优化后的提示词（直接复制）───────
```text
用大白话解释 C++ 的 RAII，先讲直觉，再给准确的一句话定义。
给一个最小代码例子，逐步说明资源何时取得、何时释放。
【推断】最后用一道判断题检查我是否理解对象生命周期如何管理资源。
```
─── 改动说明 ───────────────────
