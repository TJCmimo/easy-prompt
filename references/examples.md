# 跨领域好坏对照示例

> 转写输出的口吻、格式、解说长度以本文件为准。
> 下列示例横跨软件服务、数据分析、团队协作、社区活动、内容制作与 coding agent，示范同一套规则如何适配不同领域。

## 例 1（工程执行类·软件服务排障·金标准，含完整输出格式）

人话：帮我看看这个订单查询接口为啥最近变慢了

诊断：工程执行类；关键缺口无（目标可从“接口变慢”析出）；
背景判定：省略——用户身份或能力不会改变性能排查路线；缺材料/限制/验收；命中 AP1（“帮我看看”）。

转写输出（完整格式，逐字示范）：

─── 优化后的提示词（直接复制）───────
```text
目标：定位订单查询接口响应变慢的原因，先分析，不改代码
材料：<在此粘贴接口实现、近期请求日志、耗时指标与调用链追踪>
限制：【推断】先不要改代码；不要建议重装环境或删除文件 ← 可改
处理方法：先列可能原因并按概率排序（数据库查询/外部依赖/缓存命中率/序列化/锁竞争），再给每项的证据要求与排查步骤
验收：【推断】按概率排序的原因清单 + 每项对应的验证查询、观测指标或计时打点位置 ← 可改
```
─── 改动说明 ───────────────────
· 原话“帮我看看”目标模糊（AP1）→ 细化为“定位接口响应变慢原因，先分析不改码”
· 用户身份和能力不影响排查路线 → 背景通过删除测试后整行省略；限制和验收为【推断】
· 发送前补齐接口实现、日志、指标和调用链等材料占位符，并检查所有【推断】行

## 例 2（学习理解类·数据分析）

人话：我是刚接触数据分析的活动运营，统计基础一般，想看懂这份 A/B 测试报告里每个指标是什么意思

诊断：学习理解类；背景判定：保留——用户明确给出的工作场景和统计基础会改变解释难度与例子选择；缺材料（报告内容）；无反模式。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
```text
目标：解释这份 A/B 测试报告，先讲整体结论，再逐项说明每个指标
背景：读者负责活动运营，刚接触数据分析，统计基础一般
材料：<在此粘贴 A/B 测试报告及指标定义>
限制：【推断】不要一开始堆专业术语；每次只引入一个新概念 ← 可改
处理方法：先用活动报名场景讲直觉，再给正式定义；每个专业术语第一次出现时都解释，并区分“观察到差异”和“有足够证据支持差异”
验收：【推断】覆盖报告中的全部指标；最后用一道判断题检查我能否正确解读结论 ← 可改
```
─── 改动说明 ───────────────────
· 把“看懂指标”细化为“先讲整体结论，再逐项说明”，对应学习理解类
· 处理方法采用“先讲直觉，再讲正式定义”和“每个专业术语第一次出现时都解释”
· 你明确给出的工作场景和统计基础会改变讲解难度，因此保留；没贴报告则留下占位符
· 限制和判断题验收为【推断】，可按需修改
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 3（决策比较类·团队协作）

人话：我们是一个 6 人远程公益团队，成员每半年轮换，知识库由志愿者维护。我觉得该用 Notion，不用再看 Outline 和 GitBook 了，你说说为什么 Notion 好

诊断：决策比较类；背景判定：保留——团队规模、轮换频率和志愿维护方式会改变上手与维护成本的权重，且没有在目标或材料中重复；命中 AP2（先给结论求辩护）；缺现状材料。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
```text
目标：比较 Notion、Outline 和 GitBook 作为团队知识库的适用性，先不下结论
背景：团队共 6 人、采用远程协作、成员每半年轮换，维护工作由志愿者承担
材料：<补充现有资料量、协作流程、预算、权限与数据导出要求，以及三种工具的已核实信息>
限制：【推断】先完成全部比较再给推荐；不要顺着我已有的 Notion 倾向圆 ← 可改
处理方法：统一按上手成本、协作体验、维护投入、总成本、数据可迁移性五个维度比较并形成初步推荐；执行独立反方审查：支持多 agent 时派发一个未参与初步分析的子 agent 尝试推翻推荐，不支持子 agent 时单独做一遍同标准红队审查；最后综合反驳
验收：【推断】比较表 + 明确推荐 + 推荐理由 + 最强反方观点 + 反驳成立与否 + 最终推荐是否改变 + 什么情况下应改选其他项 ← 可改
```
─── 改动说明 ───────────────────
· 原话先认定 Notion 再求理由（AP2）→ 改为三种知识库方案先比较、最后推荐
· 用同一组维度比较，并用独立批评者专门尝试推翻初步推荐，降低主 agent 自审偏乐观的风险
· 团队规模、轮换和志愿维护方式来自原话且会改变成本判断；缺失的现状信息保留为材料占位符
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 4（猜想探索类·社区活动·两段式）

人话：我们的社区读书会只有 3 名志愿者，每月预算 500 元，除了线下分享还能有哪些新活动形式？

诊断：猜想探索类；背景判定：省略——社区读书会已在目标中，志愿者人数和预算属于资源限制；缺现状材料与收敛标准。
本例同时示范：两条提示词都逐项诊断背景，并把资源上限放入限制而不是背景。

转写输出（完整格式）：

─── 优化后的提示词 1（先发散，直接复制）───
```text
目标：探索社区读书会可以尝试的新活动形式，先不要给最终方案
材料：<补充当前活动形式、参与者画像、场地或线上平台、出席数据与反馈>
限制：可投入 3 名志愿者，每月预算不超过 500 元；【推断】现在不要收敛、不要评分排序；每个方向给一段核心思路即可 ← 可改
处理方法：从低成本线下、异步参与、成员共创、跨社群合作四个角度展开【推断-角度可换】
验收：【推断】至少 4 个方向，每个包含核心思路与主要代价 ← 标准可改
```

等 AI 展开完再发第二条，可先补充你的筛选偏好。
（补充我的筛选偏好：______）

─── 优化后的提示词 2（再收敛，直接复制）───
```text
目标：基于上一轮社区读书会候选形式，筛选并推荐最值得优先尝试的 1–2 个方向
材料：<粘贴提示词 1 的完整输出>；<补充我的筛选偏好，没有则写“无”>
限制：可投入 3 名志愿者，每月预算不超过 500 元；【推断】只基于上一轮候选和补充材料比较；不虚构社群事实 ← 可改
处理方法：按参与门槛、组织工作量、成本、可重复性统一比较【推断-标准可换】并形成初步推荐；执行独立反方审查：支持多 agent 时派发一个未参与初步分析的子 agent 尝试推翻推荐，不支持子 agent 时单独做一遍同标准红队审查；最后综合反驳
验收：【推断】推荐 1–2 个方向 + 推荐理由 + 适用边界 + 最强反方观点 + 反驳成立与否 + 最终推荐是否改变 + 第一步行动 ← 标准可改
```
─── 改动说明 ───────────────────
· 把开放的“新活动形式”判为猜想探索类，拆成先发散、再收敛两条可直接发送的提示词
· 现状信息未提供 → 第一条保留材料占位符；志愿者人数和预算来自原话并归入限制，不当作背景
· 第二条只在 AI 展开后发送，并用独立反方审查检验初步推荐；筛选标准、限制与验收中的推断均已标明
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 5（内容生成类·活动手册）

人话：帮我给第一次主持线上工作坊的志愿者写一份主持人操作手册

诊断：内容生成类；背景判定：保留——目标读者由用户明确给出并会改变写法；缺素材、格式例子与验收。

转写输出（完整格式）：

─── 优化后的提示词（直接复制）───────
```text
目标：编写线上工作坊主持人操作手册
背景：读者是第一次主持线上工作坊的志愿者
材料：<在此粘贴活动目标、平台信息、流程表、角色分工、已确认操作和常见突发情况>
限制：【推断】格式仿照下面的目标风格样例（隐式语义）；使用简体中文 Markdown ← 格式可改
处理方法：先列大纲让我确认，再写全文
验收：【推断】必须覆盖活动前准备、现场主持、突发处理和结束收尾；风格与样例一致 ← 要点可改
目标风格样例：
### 环节：<环节名称>
目标：<参与者此时应完成什么>
开始前：<主持人检查项>
主持话术：<可直接照读的一段话>
异常处理：<异常现象 → 处理动作>
```
─── 改动说明 ───────────────────
· 保留用户明确给出的读者背景，用它控制文档的术语和步骤粒度
· 你没给活动素材 → 平台、流程、分工和突发情况都只留占位符，没有代填事实
· 加入目标风格样例传递隐式语义，并用“先列大纲让我确认，再写全文”控制生成过程
· 验收补上准备、主持、突发处理和收尾四块，因原话未指定而标为【推断】可改
· 发送前检查全部【推断】并替换全部 <...> 占位符

## 例 6（会话收割·面向 coding agent）

人话：把我们刚才排查 cache shutdown 竞态的内容收成一条提示词，我要 rewind 后交给 coding agent 继续修。

会话上文已确认：唯一目标是修复 TSAN 报告的 cache shutdown 竞态；相关文件为
`src/cache.cpp`、`tests/cache_test.cpp`；失败命令和 TSAN 重跑命令已经执行并贴出结果；
240 行日志位于 `/tmp/cache-tsan.log`。AI 曾无证据断言“根因就是 ABA”，该断言不收割。

诊断：工程执行类；材料齐全，无关键缺口；长日志只收关键片段并注明来源。
面向 coding agent 且成品将在 rewind 后使用，因此采用完整字段；提示词内不留占位符。

转写输出（收割场景金标准）：

─── 优化后的提示词（直接复制）───────
```text
目标：定位并修复 Cache 关闭阶段由 `Cache::shutdown()` 与完成回调并发访问引发的数据竞争，优先最小修改

材料：
- 实现文件：`src/cache.cpp`
- 测试文件：`tests/cache_test.cpp`
- 已观察失败：`cache_test` 在关闭阶段仍收到一次完成回调
- TSAN 关键片段：
  `WARNING: ThreadSanitizer: data race`
  `Write of size 1 at Cache::shutdown() src/cache.cpp:184`
  `Previous read of size 1 at Cache::onComplete() src/cache.cpp:127`
- 完整日志来源：`/tmp/cache-tsan.log`
- 已执行失败命令：`ctest --test-dir build -R cache --output-on-failure`
- 已执行 TSAN 命令：`TSAN_OPTIONS=halt_on_error=1 ctest --test-dir build-tsan -R cache --output-on-failure`

限制：只修改消除该数据竞争所必需的代码，不改无关文件；把代码或日志能确认的事实与候选解释分开；发现其他问题先记录，除非阻塞本任务否则不处理

处理方法：沿 `Cache::shutdown()` 与 `Cache::onComplete()` 的对象生命周期、同步关系和退出顺序核对实际控制流；用上述代码与 TSAN 证据验证根因后实施最小修复；改后重跑两条命令

验收：两条命令均通过，TSAN 不再报告上述竞争；说明修改文件、根因证据、验证结果与回滚方法
```
─── 改动说明 ───────────────────
· 把已确认的文件、函数、失败现象和两条命令直接收割进材料与验收，成品不依赖旧对话。
· 240 行 TSAN 日志只保留能支持任务的关键片段，并注明完整日志来源。
· 无证据的“ABA 根因”没有写成事实；coding agent 的 rewind 场景保留完整字段且不留占位符。
· 发送前确认没有未处理的【推断】或占位符，并核对收割的路径、命令、日志片段与事实，核对后回溯发送。

## 例 7（学习理解类·日常经济概念·弹性格式最小示例）

人话：用大白话解释机会成本，并给一个日常例子。

诊断：学习理解类；单一明确目标，无需收割或粘贴材料，也无特殊限制，使用弹性格式。

转写输出（弹性格式，逐字示范）：

─── 优化后的提示词（直接复制）───────
```text
用大白话解释“机会成本”，先讲直觉，再给准确的一句话定义。
用“周末时间怎么安排”的最小例子，指出被放弃的最佳选项为什么也是成本。
【推断】最后用一道判断题检查我能否识别一个选择的机会成本。
```
─── 改动说明 ───────────────────
· 目标单一且不需要材料，压缩为三行自然语句，不套五要素标签。
· 保留“大白话 + 日常例子”，并补了一个标为【推断】的理解检查。
· 发送前检查【推断】是否符合需要；本例没有待替换的材料占位符。

## 例 8（引导采样 → 上下文回滚·两段式）

人话：我们网站每次发新版，都有一部分人打开还是旧版页面，多刷几次才变新。我不知道这毛病专业上叫什么，想让 AI 之后帮我彻底排查。

诊断：现象可描述、术语未知、且后续要做工程分析 → 命中"引导采样 → 上下文回滚"配方；
输出两条提示词：第一条只给现象"起名字"，用户核实候选术语后新开干净会话再发第二条。

转写输出（两段式，逐字示范）：

─── 优化后的提示词 1（先起名字，直接复制）───
```text
目标：帮我给下述现象"起名字"，先不要给修复方案，也不要修改代码或配置
材料：现象描述：网站部署新版后，部分用户打开仍是旧版页面，多次刷新后才显示新版；不同用户表现不一致
限制：【推断】暂时不下结论，不猜测具体根因 ← 可改
处理方法：1. 把我的描述整理成已观察到的事实；2. 给出 5–8 个可能相关的技术概念，各用一句话解释；3. 区分哪些概念有现有证据支持、哪些只是待验证的候选方向
验收：【推断】事实清单 + 候选概念清单，每个概念含一句话解释与证据状态 ← 可改
```
拿候选术语对照代码、配置和日志核实后，新开一个干净会话再发第二条。
─── 优化后的提示词 2（干净会话中的工程分析，直接复制）───
```text
目标：定位 <已命名现象，核实后填入> 的原因，先分析，不改代码和配置
材料：已确认现象：<核实后的事实清单>；候选方向：<核实后保留的概念>；<粘贴部署流程说明、缓存相关配置与响应头样本>
限制：候选方向不是已确认结论，必须从配置和日志中验证；将已确认事实、配置证据和推测分开写；【推断】不要直接重写发布流程 ← 可改
处理方法：先列可能原因并按概率排序，再说明每个原因对应的配置项、响应头字段、日志位置或最小验证方法
验收：按优先级排列的可能原因 + 每项的验证方法 + 指出下一步需要我提供哪些配置或日志
```
─── 改动说明 ───────────────────
· 现象说得清但叫不出名字、后续要工程排查 → 两段式：第一条只整理事实并给 5–8 个候选概念，明确不给修复方案
· 第二条面向核实后的干净新会话：材料只带已确认事实与候选方向，并要求事实、证据、推测分开写
· "AI 说现象可能叫 X"不等于"配置已证明就是 X"→ 两条之间必须由你核实后再发，不要在旧会话继续
· 发送前检查全部【推断】行并替换所有 <...> 占位符
